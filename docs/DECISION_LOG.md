# 구현 결정·문제·해결 기록

작성일: 2026-10-07. 이 문서는 개발 과정 글의 근거 자료이며, 공개 발행이나 성과를 주장하는 글이 아니다.

## 1. 먼저 확정 사항을 분리했다
README·PRD·TRD를 모두 읽었다. Android 8+, 글 연결 메모, 계정·백업 없음, 지연 허용 알림, 정적 JSON, 내부 APK는 사용자 결정이다. Compose·Room·WorkManager는 기술 제안으로 검토한 뒤 채택했다. Flutter는 현재의 Android-only 범위에 비해 추가 런타임과 플러그인 관리가 필요했고, 웹 셸 전체로 구현하면 개인 메모·검색·알림의 경계가 복잡해진다.

## 2. 앱과 웹 저장소를 혼동하지 않았다
앱 저장소는 문서 세 개로 시작했다. 웹 저장소는 별도 디렉터리에 두었다. 준비 중 웹 main이 갱신됐으므로 실제 clone 결과 `a9c27bbc3985cc3dd4ad5d3aff970768ec79c956`을 웹 기준으로 기록했다. 예전에 draft였던 first-vibe-coding이 현재는 공개 글이어서 테스트를 과거 상태에 맞추지 않고 별도의 가상 draft를 만들어 제외 정책을 확인했다.

## 3. JSON을 HTML 화면과 별개로 만들었다
웹의 canonical 콘텐츠 선택 로직과 최종 HTML/이미지 파이프라인을 재사용한다. 앱 계약은 schemaVersion=1과 sha256 revision을 사용하며, 상세 URL에 revision을 넣는다. HTML에는 글 부분만 남기고 허용 태그·속성 및 HTTPS URL을 검사한다. 실제 작성자 소셜 계정은 확인되지 않아 channels=[]로 제공한다.

원격 배포를 하지 않았으므로 실제 서비스에 새 피드가 있다고 주장하지 않는다. 내부 APK는 별도 웹 빌드로 검증한 8개 글의 샘플 스냅샷을 기본으로 보여주고 화면에 샘플임을 표시한다. 설정에서 실제 연결을 선택할 수 있다. 사용자 메모를 샘플에 섞어 원격으로 전송하지 않는다.

## 4. 캐시가 바뀌어도 개인 기록은 남긴다
Room DB를 content.db와 personal.db로 나누었다. Bookmark와 Memo도 별도 테이블이며, 글 하나의 북마크는 하나지만 메모는 여러 개다. 글 제목과 URL 스냅샷을 개인 DB에 저장한다. 목록에서 글이 없어지거나 캐시를 지워도 메모·알림·북마크는 남는다.

새 manifest가 왔다는 이유로 기존 HTML을 새 revision으로 바꾸지 않는다. wantedRevision과 cachedRevision을 분리하고, 실패하면 이전 본문을 읽을 수 있다. 전체 manifest가 검증된 뒤에만 사라진 글을 unavailable로 표시한다. 상세 다운로드는 UI에서 요청하면 전체 갱신 순서를 기다리지 않고 진행한다.

## 5. 한국어 검색에는 단순하고 검증 가능한 방법을 택했다
SQLite에 파라미터를 바인딩한 부분 일치 검색을 사용한다. %, _, 역슬래시는 와일드카드가 아니라 문자로 처리한다. NFC 정규화, 200자 제한, 250ms debounce, 글/메모 구분과 점진적 결과 추가를 적용했다. 검색어·메모는 네트워크 요청에 포함하지 않는다. 1,000개 글과 1,000개 메모의 실기기 성능 목표는 측정 전 달성했다고 하지 않는다.

## 6. 읽기 알림은 작은 상태 기계다
예약 시각은 epoch millis로 저장한다. 글당 한 예약과 증가하는 generation을 사용하며 수정·취소·재실행 때 이전 작업이 새 알림을 보내지 않도록 검증한다. WorkManager는 정확한 시각을 약속하지 않는다. 권한·채널이 막혀도 일정은 남기며, 재부팅·늦은 worker 복구 시 놓친 일정은 요약한다.

Room과 NotificationManager는 하나의 원자적 트랜잭션이 아니다. posting 상태를 먼저 기록하고 동일 알림 ID로 재시도하며 복구 재알림은 조용히 처리한다. 이것은 논리적 중복과 반복 소리를 줄이는 설계이지, OS 실제 표시의 exactly-once를 증명하는 것은 아니다.

## 7. 독립 검토로 고친 경계 문제
- 큰 JSON/HTML을 UI 스레드에서 파싱하지 않도록 IO 디스패처로 이동
- 메모 초안에 저장 가능한 UUID를 붙여 회전 직후 재시도가 중복 메모를 만들지 않도록 함
- 저장 중 Back/새 알림 탐색을 막고, 저장하지 않은 변경에는 선택 제공
- 알림 예약 창에 원래 글 ID를 저장해 다른 알림이 도착해도 엉뚱한 글에 예약되지 않도록 함
- 샘플/실제 연결 전환을 하나의 직렬 작업으로 처리
- 처리한 알림 Intent를 화면 회전 때 다시 실행하지 않도록 소비 상태 보존
- 개인 기록 쓰기와 전체 삭제에 같은 잠금을 사용해 삭제 직후 늦은 쓰기가 기록을 되살리지 않도록 함

## 8. 빌드 환경과 검증의 정직한 경계
이 작업의 클라우드에는 JDK는 있었지만 Android SDK는 없었다. Gradle 8.11.1 배포 파일은 공식 checksum으로 검증했고, 환경별 프록시 주소와 쓰기 가능한 Gradle/Android 사용자 경로를 구성했다. Android SDK 약관은 10:38 UTC 사용자 승인 후 10:40 UTC 실제 수락했다. SDK 35/build-tools 35.0.0을 설치했고, 기존 Java에는 javac 실행 파일이 없어 공식 Temurin JDK 17.0.20.1+1을 추가했다. 공식 배포 SHA-256을 대조했다.

실제 실행한 명령·성공/실패·미실행 기기 항목은 TEST_REPORT.md에 기록한다. 빌드 성공, 자동화 테스트 성공, 에뮬레이터 성공, 실기기 성공은 서로 대체하지 않는다. 원격 push·PR·배포는 진행하지 않는다.

## 9. 자동화와 에뮬레이터에서 발견한 실제 문제
Android 소스를 컴파일하고 Room schema v1을 생성한 뒤, 전체 52개 JVM/Robolectric 테스트와 lint를 실행했다. 읽기/검색/메모/알림의 테스트 환경도 실제 Android 런타임을 사용하는 검사로 확대했다.

- 테스트 코드의 쓰지 않는 Espresso import와 JUnit이 요구하는 void 반환 형식을 수정했다
- Robolectric의 WorkManager 초기화와 쓰기 가능한 캐시 경로를 테스트 환경에 명시했다. 실제 앱의 AndroidX Startup 동작은 에뮬레이터에서 따로 확인한다
- API 26 AOSP 이미지에 시스템 WebView가 아예 없었다. 표면적으로 보인 Compose 종료 중 예외만 보고 라이브러리를 바꾸지 않고 최초 원인인 MissingWebViewPackageException을 확인했다
- WebView가 없거나 비활성화된 기기에서는 앱을 종료시키지 않고 캐시된 본문을 선택 가능한 텍스트로 보여주도록 폴백을 추가했다. 이미지·서식 표시 제한을 화면에 알린다
- WebView 해제는 AndroidView.onRelease에서 처리하고 화면 폐기 도중 Compose 상태를 변경하지 않도록 했다
- 메모 입력 직후 같은 프레임에 Back이 오는 경우, 이전 recomposition의 dirty 값을 참조하던 문제가 있었다. Back 콜백 실행 시 현재 입력값을 비교하도록 바꾸자 해당 회귀 테스트가 통과했다

최종 자동화 결과와 각 에뮬레이터의 실제 확인 범위는 TEST_REPORT.md를 기준으로 한다. 소프트웨어 에뮬레이터의 느린 부팅/성능을 실기기 성능으로 해석하지 않는다.

## 10. 마지막 의존성과 최신 웹 기준을 정리했다
웹 main이 `6ffd29e21f292dda046b83664101f2e597f734ee`로 바뀐 것을 확인해, 별도 새 디렉터리에 기존 피드 패치를 적용했다. 최신 AstroContainer/OG-image 변경을 보존한 채 root와 subpath 각각 47개 테스트 및 HTTP·14개 이미지 확인을 통과했다. 8개 글의 상세 바이트와 revision은 같아 앱 샘플을 불필요하게 다시 생성하지 않았다.

소프트웨어 에뮬레이터 설치 로그에서 material-icons-extended의 사용하지 않는 수많은 벡터 메서드를 ART가 검증하는 것을 확인했다. 실제 쓰는 여섯 아이콘을 작은 앱 벡터 리소스로 바꾸고 공통 core 아이콘만 남겼다. 깨끗한 빌드의 APK는 18,042,948바이트에서 10,474,638바이트로 줄었다. 마지막 clean aggregate는 86개 task를 모두 다시 실행해 52개 테스트와 lint를 통과했다. 이는 에뮬레이터 설치 병목을 줄이는 조치이며, 실기기 앱 실행 성능 수치를 주장하는 것은 아니다.
